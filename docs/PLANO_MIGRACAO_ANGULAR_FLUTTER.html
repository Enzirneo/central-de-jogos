02

Protocolo de comunicação (o ponto crítico)

O servidor hoje manda dados pro cliente de duas formas:

  1. @colyseus/schema (binário, sincronização automática) — para o LobbyState: código da sala, fase, lista de jogadores, host.
  2. Mensagens JSON via client.send("evento", payload) — para o estado do jogo (game_state, game_over, start_game_error).

O cliente JS/Angular decodifica schema de graça com colyseus.js. O cliente Dart precisa de um decodificador de schema compatível.

2.1 · Decisão: schema vs JSON para o lobby

Decidido — protocolo 100% JSON

O servidor não expõe @colyseus/schema aos clientes. O LobbyState schema vira detalhe interno (ou é removido) e o servidor faz broadcast("lobby_state", <JSON>) a cada mudança relevante.

Por quê: o schema é um formato binário que exige um decoder da mesma versão nos dois lados. colyseus.js traz o decoder pro Angular, mas o cliente Dart dependeria de um pacote comunitário que pode não acompanhar o @colyseus/schema ^3.0.0. Um protocolo 100% JSON é idêntico pros dois clientes, versionável e depurável (dá pra ver as mensagens no navegador).

Custo aceito: perde-se a sincronização incremental automática — o servidor manda o estado inteiro do lobby a cada mudança. É barato: < 12 jogadores.

Transporte: dá pra usar o pacote colyseus do pub.dev só para conexão e matchmaking (handshake joinOrCreate + reconexão), consumindo apenas mensagens JSON e nunca room.state. Alternativa: web_socket_channel + replicar o handshake HTTP à mão. Decidir no scaffold do Flutter (Fase 3).

2.2 · Eventos

Entrada na sala: client.joinOrCreate("lobby", { code?, nickname }) — sem code cria sala nova; com code entra na existente (filterBy(["code"])).

Cliente → servidor

EventoPayloadRegra
select_game{ gameId, options? }Só o host. Só na fase lobby. Valida catálogo e nº de jogadores.
toggle_ready—Só na fase starting. Alterna o "pronto" do jogador.
cancel_start—Só o host. Volta pra lobby.
game_actionunknown (cada jogo valida)Só na fase playing. Roteado pra plugin.applyAction.

Servidor → cliente

EventoPayloadQuando
lobby_state (se Plano C)estado do lobby em JSONA cada mudança. (Na Opção A isso é o schema.)
game_stateplugin.getStateForPlayer(state, sessionId)A cada game_action; e ao entrar no meio de uma partida. Individual por jogador (esconde info).
game_overplugin.getResults(state)Quando isGameOver vira true. Sala volta pra lobby.
start_game_error{ message }Ação inválida (não é host, jogadores de menos, jogo inexistente...).

Fases da sala: lobby → starting (host propôs, aguarda todos "prontos") → playing → volta pra lobby (maratona de jogos na mesma sala).

Reconexão: já implementada — allowReconnection(client, 60). O cliente guarda o reconnectionToken e tenta client.reconnect(token) ao cair.

Angular — como estruturar (apps/web)

"Bem estruturado" = arquitetura por features, standalone components, separação smart/dumb, estado em signals.

4.1 · Setup

  • ng new web: standalone (sem NgModules), SCSS, routing, sem SSR de início.
  • Registrar como workspace npm: scripts dev (ng serve), build, lint, test.
  • Runner: Karma foi descontinuado. Usar Vitest (@angular/build:unit-test ou @analogjs/vitest-angular). Alinha com o npm test do monorepo.
  • ESLint via angular-eslint — ligar só em apps/web.

4.2 · Pastas

PastaO que mora aqui
core/colyseus/colyseus.service.ts (conexão, joinOrCreate, reconnect) · room.store.ts (signals: sala, jogadores, fase, host, erros)
core/config/app-config.ts — URL do servidor por ambiente
core/game-registry.tsid do catálogo → () => import(componente)
shared/ui/botão, card, layout, avatar — SCSS + tokens (dumb, OnPush)
features/{home,lobby,ready-check,game-host}/telas smart (injetam o store)
features/games/ito/ito-clue/ ito-board/ ito-reveal/ ito-results/ + ito.routes.ts

4.3 · Padrões

  • Estado: RoomStore providedIn: 'root' expondo signals. O ColyseusService converte eventos do socket em fluxo e atualiza os signals. Sem NgRx (overkill); trocável por SignalStore depois sem mexer nos componentes.
  • Smart vs dumb: features/ injetam o store; shared/ui/ só input()/output(), OnPush, zero serviço.
  • Roteamento: lazy por feature. / home · /sala/:code lobby · /sala/:code/jogar game-host, que faz import() dinâmico do jogo via game-registry.
  • Contrato de jogo no cliente: GameClientPlugin { id; loadComponent(); } num mapa — espelha o registry.ts do servidor.
  • Estilo: styles/_tokens.scss (cores, espaçamento, tipografia). Considerar Angular CDK sem Material.

4.4 · Testes

  • Lógica pura (mapeadores estado→view, validações de form) primeiro, com Vitest.
  • Componentes: @testing-library/angular + asserção de comportamento visível.
  • RoomStore: ColyseusService fake (Mock Object — ver .claude/rules/tdd.md).

Flutter — como estruturar (apps/mobile)

5.1 · Setup

  • flutter create --org com.centraldejogos --platforms=ios,android mobile dentro de apps/.
  • Dependências principais:
    • Transporte (§2.1): pacote colyseus do pub.dev só para conexão/matchmaking/reconexão, consumindo JSON e nunca room.state; ou web_socket_channel + handshake HTTP à mão. Decidir no scaffold.
    • flutter_riverpod — estado (testável, sem boilerplate; bom pra treino). Alternativa: flutter_bloc.
    • go_router — navegação declarativa.
    • freezed + json_serializable + build_runner — modelos imutáveis do protocolo.
  • Lints: flutter_lints — considerar very_good_analysis.

5.2 · Pastas

PastaO que mora aqui
core/colyseus/colyseus_client.dart (connect, joinOrCreate, reconnect) · room_controller.dart (Riverpod Notifier: estado da sala)
core/config/app_config.dartURL do servidor por ambiente (--dart-define)
core/game_registry.dartid do catálogo → WidgetBuilder
models/espelho de docs/contrato-wire.md (freezed): lobby_state.dart, player.dart, game_results.dart, events.dart
shared/widgets/botão, card, layout — widgets pequenos
features/{home,lobby,ready_check,game_host}/telas
features/games/ito/ito_clue_screen.dart, ito_board_screen.dart, ...

5.3 · Padrões

  • Estado: RoomController (Riverpod Notifier) assina eventos do ColyseusClient e expõe um RoomState imutável. Widgets fazem ref.watch.
  • Lógica fora da UI: nada de regra no build(). Mapeadores estado→viewmodel em funções puras testáveis.
  • Widgets pequenos (clean-code §2/§9): extrair Widget privado em vez de método _buildX().
  • Contrato de jogo no cliente: typedef GameBuilder = Widget Function(GameContext ctx) num Map<String, GameBuilder>.
  • Ambiente: --dart-define=SERVER_URL=ws://10.0.2.2:2567 (emulador Android → host via 10.0.2.2).
  • Modelos: gerados de JSON com freezed. docs/contrato-wire.md é a fonte — mudança no protocolo atualiza o doc e os dois lados.

5.4 · Testes

  • flutter test: unidade dos mapeadores puros e do RoomController (com ColyseusClient fake).
  • Widget tests das telas principais (lobby, ITO).

Mudanças no servidor (apps/server)

Pequenas, mas necessárias:

  1. Renomear import @central-de-jogos/shared-types → @central-de-jogos/protocol.
  2. Validar payloads de entrada com zod (select_game, game_action, opções de join) — hoje confia no shape.
  3. CORS / origens permitidas: liberar http://localhost:4200 (Angular dev) e o app Flutter. Adicionar ALLOWED_ORIGINS ao .env.example.
  4. Protocolo JSON (§2.1, decidido): broadcast("lobby_state", toJSON(this.state)) nos pontos de mudança; LobbyState schema vira interno ou é removido.
  5. game_over → também mandar lobby_state atualizado (a sala volta pra lobby).
  6. Teste de integração de sala com @colyseus/testing (lobby → starting → playing → game_over).
  7. .env.example: revisar chaves (Postgres, Redis, PORT, ALLOWED_ORIGINS).
Nota

Nenhuma dessas mexe em packages/games/* — a lógica de jogo e seus testes ficam intactos. Os hooks de TDD continuam válidos sem alteração (só olham packages/games/*/src).

Roadmap de execução

Cada fase é uma ou mais branches tipo/descricao a partir de dev, com npm test + npm run lint verdes antes do merge (.claude/rules/gitflow.md).

Fase 0

Limpeza, contrato e CI

  1. chore/remove-clientes-react — apagar apps/mobile-web e packages/ui; ajustar package.json raiz, turbo.json, .gitignore. Servidor tem que continuar buildando e npm test verde.
  2. refactor/renomeia-protocol — packages/shared-types → packages/protocol; atualizar imports.
  3. feat/protocol-eventos — events.ts + events.schema.ts (zod) + testes. Servidor valida entradas.
  4. Escrever docs/contrato-wire.md — Markdown: tabela por evento (nome, direção, quando dispara) + JSON de exemplo + notas de reconexão e erro.
  5. ci/github-actions — workflow rodando npm run lint + npm test a cada push/PR pra dev. (flutter test entra na Fase 3.)
Fase 1

Servidor pronto para dois clientes

  1. feat/server-cors-json — CORS/origens; protocolo JSON (§2.1): broadcast("lobby_state", <JSON>) nos pontos de mudança; LobbyState schema vira interno ou é removido; game_over passa a mandar lobby_state também.
  2. test/server-fluxo-sala — teste de integração com @colyseus/testing.
  3. Fechar docs/contrato-wire.md com o protocolo final.
Fase 2

Web (Angular) MVP

  1. feat/web-scaffold — ng new, workspace npm, Vitest, angular-eslint, estrutura. Design system: o usuário fornece a referência visual e o _tokens.scss + componentes-base são montados aqui. Página vazia compilando + CI passando.
  2. feat/web-colyseus-core — ColyseusService + RoomStore (signals) + testes com fake.
  3. feat/web-lobby — home, lobby (host escolhe jogo), ready-check.
  4. feat/web-game-host — container troca componente por activeGameId; registry; template game ponta a ponta.
  5. feat/web-ito — telas do ITO (clue / board / reveal / results).
  6. chore/web-deploy — build estático na Vercel.
Fase 3

Mobile (Flutter) MVP

  1. feat/mobile-scaffold — flutter create --platforms=ios,android, deps, estrutura, ThemeData + widgets-base a partir da mesma referência visual da web, flutter analyze/test verdes. Adicionar flutter test ao CI. Execução e testes só em Android — iOS compatível no código, sem build.
  2. feat/mobile-colyseus-core — transporte (§2.1) + RoomController + modelos freezed + testes com fake.
  3. feat/mobile-lobby — home, lobby, ready-check.
  4. feat/mobile-game-host — registry + template game ponta a ponta.
  5. feat/mobile-ito — telas do ITO.
  6. Build Android: flutter build apk local, sob demanda. Sem pipeline automatizado (nem Android nem iOS).
Fase 4

Paridade, escala e deploy

  1. Revisar paridade de features entre web e mobile (lobby + template + ITO).
  2. test/multi-sala — várias salas simultâneas, ajustar driver Redis do Colyseus.
  3. Decidir a hospedagem do servidor (Fly.io / Render / VPS — ver §11) e subir um ambiente: servidor + Redis + Postgres gerenciados, web na Vercel.
  4. docs/atualiza-claude-md — reescrever CLAUDE.md conforme §8.
Fase 5

Novos jogos (contínuo)

  1. Por jogo: plugin TS + testes → catálogo → componente Angular → widget Flutter. Documentar o ciclo no CLAUDE.md.
